# Postman Collection Update Proposal

## Change Summary (2026-09-09)

Three new endpoint groups were added to `routes/web.php`:

1. **`/events` route completed** — the truncated line was finished; now merges `Event` records
   with approved `EventRequest` records and returns a unified calendar array.
2. **`EmergencyRecoveryController` routes** — two dedicated recovery routes using a Blade view
   (`GET /emergency/recovery`, `POST /emergency/unlock-reset`).
3. **`AdminController::emergencyUnlock` simple route** — the existing inline HTML form endpoint
   previously added (`Route::any('/emergency-unlock')`), already documented below.

Five new requests have been added to the collection (`total_requests` is now **35**).

---

## Affected Endpoints

### 1. GET `/events`
- **Method:** GET
- **Auth:** None (public route)
- **Description:** Returns a merged array of all `Event` records and approved `EventRequest`
  records, formatted as `[{ title, start }]` for calendar consumption.
- **Expected Response:** `200 OK`, JSON array

### 2. GET `/emergency/recovery`
- **Method:** GET
- **Auth:** None (public route)
- **Description:** Renders the Blade view `emergency.recovery` — a Bootstrap form for
  submitting an emergency account unlock + password reset.
- **Expected Response:** `200 OK`, `Content-Type: text/html`

### 3. POST `/emergency/unlock-reset`
- **Method:** POST
- **Auth:** None (public route)
- **Headers:**
  - `Content-Type: application/x-www-form-urlencoded`
- **Body (form-urlencoded):**

  | Field           | Type   | Required | Notes                                   |
  |-----------------|--------|----------|-----------------------------------------|
  | `_token`        | string | Yes      | Laravel CSRF token                      |
  | `email`         | string | Yes      | Email of the account to recover         |
  | `new_password`  | string | Yes      | Min 8 characters                        |
  | `emergency_key` | string | Yes      | One of the hardcoded static keys below  |

- **Valid keys (hardcoded — see security issues):**
  - `CAMPFIX_EMERGENCY_2026`
  - `FRANCK_RECOVERY_KEY`
  - `ADMIN_UNLOCK_ACCESS`
- **Success:** `302` redirect back with `success` flash containing recovery summary
- **Failure:** `302` redirect back with `error` flash

### 4. GET `/emergency-unlock`
- **Method:** GET
- **Auth:** None (public route)
- **Description:** Returns an inline HTML page (rendered from the controller, not a Blade view)
  containing the simple unlock form. Key hint is embedded in the page source.
- **Expected Response:** `200 OK`, `Content-Type: text/html`

### 5. POST `/emergency-unlock`
- **Method:** POST
- **Auth:** None (public route)
- **Headers:**
  - `Content-Type: application/x-www-form-urlencoded`
  - `Accept: text/html,application/xhtml+xml`
- **Body (form-urlencoded):**

  | Field           | Type   | Required | Notes                               |
  |-----------------|--------|----------|-------------------------------------|
  | `_token`        | string | Yes      | CSRF token from the GET form        |
  | `email`         | string | Yes      | Email of the locked account         |
  | `new_password`  | string | Yes      | Min 8 characters                    |
  | `emergency_key` | string | Yes      | One of the valid static keys below  |

- **Valid keys:** same as #3 above
- **Success:** `302` redirect to `/emergency-unlock` with `success` flash
- **Failure:** `302` redirect back with error on `emergency_key` or `email` field

## ⚠️ Security Issues Found

All issues from the 2026-08-25 review still apply. Additional finding from `EmergencyRecoveryController`:

### CRITICAL — Hardcoded Keys in Two Controllers

Both `AdminController::emergencyUnlock` and `EmergencyRecoveryController::unlockAndReset`
define the same `$validKeys` array in plain text. The inline HTML form in `AdminController`
also prints the key directly:

```html
<small>Use: CAMPFIX_EMERGENCY_2026</small>
```

Fix both controllers to read from `.env`:

```php
// .env
EMERGENCY_UNLOCK_KEY=<randomly-generated-secret>

// Controller
$validKeys = array_filter([config('app.emergency_unlock_key')]);
if (empty($validKeys) || !in_array($request->emergency_key, $validKeys)) {
    return back()->withErrors(['emergency_key' => 'Invalid emergency key provided.']);
}
```

Remove the `<small>` hint in `AdminController`.

---

### CRITICAL — Password Echoed Back in Success Flash (EmergencyRecoveryController)

```php
$message .= "🔑 New Password: {$request->new_password}\n";
return back()->with('success', $message);
```

The plaintext password is stored in the session flash and rendered in the HTML response.
Anyone who can intercept the HTTP response, view session storage, or read server logs will
see the password in cleartext.

**Fix:** Remove the new password from the flash message entirely:

```php
$message = "Emergency recovery completed for '{$user->name}'. You can now log in with your new password.";
return back()->with('success', $message);
```

---

### HIGH — No Rate Limiting on Either Recovery Route

Both `/emergency/recovery` + `/emergency/unlock-reset` and `/emergency-unlock` are missing
`throttle:` middleware. Apply to both:

```php
// routes/web.php
Route::get('/emergency/recovery', [...'showForm'])->name('emergency.recovery');
Route::post('/emergency/unlock-reset', [...'unlockAndReset'])
    ->middleware('throttle:5,10')
    ->name('emergency.unlock-reset');

Route::match(['get', 'post'], '/emergency-unlock', [AdminController::class, 'emergencyUnlock'])
    ->middleware('throttle:5,10')
    ->name('emergency.simple.unlock');
```

---

### HIGH — User Enumeration in Both Controllers

`EmergencyRecoveryController`:
```php
return back()->with('error', 'User not found with email: ' . $request->email);
```

`AdminController`:
```php
return back()->withErrors(['email' => 'User not found with email: ' . $request->email]);
```

Both leak whether an email is registered. Replace with a generic message in both.

---

### MEDIUM — `Route::any()` Should Be `Route::match(['get','post'])`

```php
// Current
Route::any('/emergency-unlock', ...)

// Fix
Route::match(['get', 'post'], '/emergency-unlock', [AdminController::class, 'emergencyUnlock'])
    ->middleware('throttle:5,10')
    ->name('emergency.simple.unlock');
```

---

### MEDIUM — Duplicate Functionality Across Two Controllers

`AdminController::emergencyUnlock` and `EmergencyRecoveryController::unlockAndReset` do the
same job (unlock + password reset using a static key). Having two endpoints for the same
function doubles the attack surface and maintenance burden.

**Recommendation:** Consolidate into `EmergencyRecoveryController` (which uses a Blade view
and is more polished) and remove the inline-HTML version from `AdminController`. Redirect
`/emergency-unlock` to `/emergency/recovery` if backward compatibility is needed.

## Change Summary (2026-09-10)

## Affected Endpoints

### 1. POST `/api/push/subscribe`
- **Method:** POST
- **Auth:** Bearer JWT (`{{token}}`)
- **Description:** Creates or updates a Web Push subscription for the authenticated user.
  Stores `endpoint`, `keys.p256dh`, and `keys.auth` in the `push_subscriptions` table.
- **Expected Response:** `200 OK`, JSON `{ success, message, subscription_id }`
- **Validation errors:** `422` if `endpoint`, `keys.p256dh`, or `keys.auth` are missing.

### 2. POST `/api/push/unsubscribe`
- **Method:** POST
- **Auth:** Bearer JWT (`{{token}}`)
- **Description:** Deletes the push subscription matching the given `endpoint` for the
  authenticated user.
- **Expected Response:** `200 OK`, JSON `{ success, message }`
- **Validation errors:** `422` if `endpoint` is missing.

### 3. GET `/api/push/status`
- **Method:** GET
- **Auth:** Bearer JWT (`{{token}}`)
- **Description:** Returns whether the authenticated user has any active push subscriptions
  and the total subscription count.
- **Expected Response:** `200 OK`, JSON `{ success, subscribed, subscription_count }`

## ⚠️ Issues Found

### MEDIUM — Push Routes Indentation Bug (cosmetic, no runtime impact)

In `routes/api.php` the three push routes are indented one level short relative to the
surrounding `jwt.auth + throttle:api` group:

```php
Route::middleware(['jwt.auth', 'throttle:api'])->group(function () {

    // Push Notifications          ← these three lines are at the same indent
    Route::post('/push/subscribe', ...);   // as the outer group body, which is
    Route::post('/push/unsubscribe', ...); // correct PHP but inconsistent style
    Route::get('/push/status', ...);

    // Concerns …
```

The routes are correctly *inside* the closure so middleware applies. Align indentation for
consistency:

```php
Route::middleware(['jwt.auth', 'throttle:api'])->group(function () {

        // Push Notifications
        Route::post('/push/subscribe',   [PushNotificationController::class, 'subscribe']);
        Route::post('/push/unsubscribe', [PushNotificationController::class, 'unsubscribe']);
        Route::get('/push/status',       [PushNotificationController::class, 'status']);
```

### MEDIUM — No `PushSubscription` Model Guard Check

`PushNotificationController::subscribe` calls `Auth::user()` after the validator but the
`jwt.auth` middleware already guarantees a user. The second `if (!$user)` guard in
`unsubscribe` and `status` is redundant given the middleware stack. Not a bug, just dead
code — remove or replace with `$user = $request->user()` for clarity.

### LOW — `subscription_count` Cap Not Enforced

A user can accumulate unlimited subscription rows (one per unique endpoint). Consider
capping at a reasonable number (e.g. 5 per user) to prevent table bloat:

```php
// Inside subscribe(), before updateOrCreate:
$existing = PushSubscription::where('user_id', $user->id)->count();
if ($existing >= 5 && !PushSubscription::where('user_id', $user->id)
        ->where('endpoint', $request->input('endpoint'))->exists()) {
    return response()->json([
        'success' => false,
        'message' => 'Subscription limit reached. Unsubscribe a device first.',
    ], 422);
}
```
