# Postman Collection Update Proposal

## Change Summary (2026-08-25)

Added `emergencyUnlock` endpoint to `AdminController`. This is a public, unauthenticated
route (`Route::any('/emergency-unlock', ...)`) that renders an HTML unlock form on GET and
processes an account unlock + password reset on POST, gated only by a static emergency key.

Two new requests have been added to the collection (`total_requests` is now **30**).

---

## Affected Endpoints

### 1. GET `/emergency-unlock`
- **Method:** GET
- **Auth:** None (public route)
- **Description:** Returns a raw HTML page containing the emergency unlock form.
- **Expected Response:** `200 OK`, `Content-Type: text/html`

### 2. POST `/emergency-unlock`
- **Method:** POST
- **Auth:** None (public route)
- **Headers:**
  - `Content-Type: application/x-www-form-urlencoded`
  - `X-CSRF-TOKEN: {{csrf_token}}` *(or use the `_token` body field)*
- **Body (form-urlencoded):**

  | Field           | Type     | Required | Notes                              |
  |-----------------|----------|----------|------------------------------------|
  | `_token`        | string   | Yes      | CSRF token from the GET form       |
  | `email`         | string   | Yes      | Email of the locked account        |
  | `new_password`  | string   | Yes      | Min 8 characters                   |
  | `emergency_key` | string   | Yes      | One of the valid static keys below |

- **Valid emergency keys (hardcoded in source):**
  - `CAMPFIX_EMERGENCY_2026`
  - `FRANCK_RECOVERY_KEY`
  - `ADMIN_UNLOCK_ACCESS`

- **Success Response:** `302` redirect to `/emergency-unlock` with flash `success` message
- **Failure Responses:**
  - Invalid key → redirect back with `emergency_key` error
  - Unknown email → redirect back with `email` error
  - Exception → redirect back with `general` error

## ⚠️ Security Issues Found

The following issues were identified during code review of the new endpoint and **must be
addressed before deploying to production**.

### CRITICAL — Hardcoded Emergency Keys in Source Code

**File:** `app/Http/Controllers/AdminController.php`

```php
$validKeys = ['CAMPFIX_EMERGENCY_2026', 'FRANCK_RECOVERY_KEY', 'ADMIN_UNLOCK_ACCESS'];
```

- The emergency keys are committed to source control in plain text.
- Anyone with read access to the repository can unlock and reset any account.
- `CAMPFIX_EMERGENCY_2026` is also displayed in the HTML hint text (`<small>Use: CAMPFIX_EMERGENCY_2026</small>`), making it fully public.

**Fix:** Move keys to `.env` and load via `config()`:

```php
// .env
EMERGENCY_UNLOCK_KEY=<randomly-generated-secret>

// config/app.php or a dedicated config file
'emergency_unlock_key' => env('EMERGENCY_UNLOCK_KEY'),

// Controller
$validKeys = [config('app.emergency_unlock_key')];
if (!in_array($request->emergency_key, $validKeys) || empty($validKeys[0])) {
    return back()->withErrors(['emergency_key' => 'Invalid emergency key provided.']);
}
```

Also remove the `<small>` hint from the rendered HTML entirely.

---

### HIGH — No Rate Limiting on the Emergency Unlock Route

**File:** `routes/web.php`

```php
Route::any('/emergency-unlock', [AdminController::class, 'emergencyUnlock'])->name('emergency.simple.unlock');
```

No `throttle:` middleware is applied. An attacker can brute-force the emergency key or
enumerate valid email addresses at full speed.

**Fix:**

```php
Route::any('/emergency-unlock', [AdminController::class, 'emergencyUnlock'])
    ->middleware('throttle:5,10') // 5 attempts per 10 minutes
    ->name('emergency.simple.unlock');
```

---

### HIGH — User Enumeration via Distinct Error Messages

The controller returns different error messages for "wrong key" vs "email not found":

```php
// Leaks whether the email exists
return back()->withErrors(['email' => 'User not found with email: ' . $request->email]);
```

An attacker who knows (or guesses) a valid key can enumerate all registered emails.

**Fix:** Return the same generic message regardless of which check failed:

```php
return back()->withErrors(['general' => 'Recovery failed. Please check your details and try again.']);
```

---

### MEDIUM — `Route::any()` Accepts All HTTP Methods

```php
Route::any('/emergency-unlock', ...)
```

`Route::any()` also matches DELETE, PUT, PATCH, HEAD, OPTIONS, etc. The endpoint only
handles GET and POST logic — all other verbs fall through to the POST validator with
potentially unexpected behaviour.

**Fix:** Use `Route::match(['get', 'post'], ...)` instead:

```php
Route::match(['get', 'post'], '/emergency-unlock', [AdminController::class, 'emergencyUnlock'])
    ->middleware('throttle:5,10')
    ->name('emergency.simple.unlock');
```

---

### LOW — Emergency Key Hint Exposed in HTML Response

The GET response embeds the key directly in the page:

```html
<small>Use: CAMPFIX_EMERGENCY_2026</small>
```

Remove this hint. It effectively makes the key public to anyone who visits the URL.
